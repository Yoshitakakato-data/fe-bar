# ビルドノート — AI（Isaac / Claude Code）との作り方と、試行錯誤の記録

このデモは Isaac（Databricks 社内の Claude Code）をペアプログラマとして作った。
ここには「AI に何を作らせたか」ではなく、**どこで失敗し、どう判断して直したか**を、実際に起きた順に残す。
ログの一次資料は `evidence/databricks/RUN_LOG.md`（Databricks 上の全実行ログ）。

## ワークフロー

1. **KPI から逆算**：最初に `src/common.py` に誤検知コスト・調査分数・人件費を置き、
   「ネット金額改善」「レビュー件数」「判断標準化率」を出すことをゴールにした。
2. **ローカルで一気通貫**：numpy だけで データ生成 → パイプライン → GBDT → 理由コード → KPI → 運用ストア → App を
   `./run_all.sh` で通し、出力をテキストでコミット（`outputs/`, `logs/`）。
3. **Databricks ネイティブへ 1:1 移植**：同じ列名・しきい値で Lakeflow / UC / MLflow / Lakebase / Apps / Genie に置換。
4. **実ワークスペースで実行して証跡化**：`databricks/deploy/deploy.py` が FEVM 上で全工程を実行し、
   API 応答を `evidence/databricks/` に保存（レビューで「設計だけで未実行」と指摘されたため追加）。

## 試行錯誤の記録（実際に起きた順）

### 1. 合成データを「わざと難しく」した設計判断
合成データは放っておくと、不正が金額・国だけでほぼ分離でき、精度が現実離れして高くなりがち。
それではしきい値やEVの議論が成立しないため、生成の段階から**不正の3割を正常取引に紛れる「ステルス型」**にし、
**高額海外送金などの「怪しいが正当」な取引**も混ぜた（`src/generate_data.py`）。結果は ROC-AUC ≈ 0.89〜0.90 の
「現実的に難しい」信号で、precision/recall のトレードオフに意味が出る。
（レビューでも「hard signal を学ばせている」点が評価された）

### 2. 「説明」を近似にしない判断
SHAP 相当の理由コードを、ローカルでは numpy で木経路寄与として自作した。
「それっぽい説明」では監査に耐えないため、**全件で baseline + Σ寄与 = logit を検算**する処理を入れた。
ローカルの誤差は ~1e-15。Databricks 版（sklearn + shap.TreeExplainer）も同じ検算をノートブックに入れ、
実ワークスペースで **最大誤差 1.5e-11** を確認した（`evidence/databricks/04_ml_training.json`）。

### 3. Genie を「シミュレーション」で済ませていた → 実デプロイへ
初版の Genie は、6問の質問文と人手で書いた SQL をローカル sqlite で実行するだけだった。
レビューで「自然言語→SQL をエージェントがやっていない」と指摘されたため、
Genie Space を API で作成し、同じ6問＋フォローアップを `start-conversation` で投げ、
**Genie が生成した SQL と回答をそのまま記録**する方式に変えた（`outputs/genie_live_transcript.md`）。

### 4. Lakeflow が「テーブルが1つもない」で失敗
実ワークスペースで初回実行したら `NO_TABLES_IN_PIPELINE`。原因はノートブックのソース形式で、
`# MAGIC %md` の見出しと `@dlt.table` のコードを同じセルに書いていたため、**セル全体が Markdown 扱い**になっていた。
ローカル実行では顕在化しないバグ。セルを分割して解決（学習ノートブックにも同じ問題があり同時に修正）。

### 5. パイプラインの自動リトライと手動更新の衝突
設定更新後に再実行すると `An active update already exists`。失敗時の自動リトライ（RETRY_ON_FAILURE）が
裏で走っていた。デプロイスクリプトに「停止 → IDLE を待つ → フルリフレッシュ」の手順を入れた。

### 6. FEVM ではアカウントグループが作れない → ガバナンスの見せ方を再設計
UC の GRANT はアカウントグループにしか付与できず、FEVM にはアカウント管理者権限がない。
GRANT が失敗するのは隠さず記録したうえで、マスク関数・行フィルタ関数を
`is_account_group_member()`（本番）と `is_member()`（ワークスペースグループ）の両方で判定するようにした。
効き目は **同じユーザ・同じ SQL** でグループ所属の前後を比べて証明した：
海外送金の可視行数 0 → 2,034、顧客IDは `C******000` にマスク（`evidence/databricks/05_unity_catalog_part_b.json`）。

### 7. 認証情報をローカルに出さない
Lakebase の OAuth 資格情報をローカルで発行して psql 的に接続しようとしたところ、
開発環境の安全ポリシーで止められた（ローカルに PyPI もなく Postgres ドライバも入れられなかった）。
正しい方向だと判断し、**Postgres 側の操作はすべてサーバレス Job（`07_lakebase_sql.py`）の中で資格情報を発行・使用**し、
結果行だけを返す設計にした。App の疎通確認も、App 自身が起動時に Lakebase を読み・書きして
`app_selfcheck` に記録し、それを Job から確認する方式にした。

### 8. Lakebase の同期元を絞る
アナリスト向けの `scored_transactions` には列マスク・行フィルタを掛ける一方、App のサービスプリンシパルは
運用キューを全件読む必要がある。そこで「判断が必要な取引（REVIEW / BLOCK_CANDIDATE）」だけの
`scored_transactions_ops` を同期元にした。運用ストアは小さく、分析側は統制下、という役割分担。

### 9. LLM は「判断」ではなく「説明文の整形」だけに使う
レビューの発展提案を受けて `ai_query` による対応メモを追加したが、ブロック/承認の判断はあくまで ML＋EV。
LLM への入力は UC 管理下の理由コードと EV のみとし、「データにない事実を足さない」ことをプロンプトで明示した。
判断の再現性・監査性を LLM に依存させないためのトレードオフ。

## 主なトレードオフ

| 判断 | 採用 | 捨てたもの | 理由 |
|---|---|---|---|
| 不正判定のモデル | 勾配ブースティング（クラシックML） | LLM による判定 | 表形式・大量ラベルに強く、加法的寄与で**厳密に**説明できる |
| 判断基準 | EV（円）＋しきい値ポリシー | 生スコアのみ | 確率・金額・誤検知コストを1つの業務指標に統合 |
| 人の関与 | 97.7% を機械確定、残りを人が理由付きで判断 | 全件人手 / 全自動 | 工数削減と、グレーゾーンの説明責任の両立 |
| データ | 合成データ（PIIなし） | 実データ | 前提は `src/common.py` に集約し、顧客KPIで再較正できる形に |
| GenAI の使いどころ | 説明文の整形（対応メモ）と Genie の探索 | 判断そのもの | 再現性と監査性を守る |
